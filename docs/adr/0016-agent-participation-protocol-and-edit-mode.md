# ADR-0016: 에이전트는 어떤 프로토콜로 문서에 참여하고, 편집은 기본적으로 어떻게 반영되는가

> **proposed (2026-09-26)**
>
> - 비교안과 추천안은 에이전트가 작성했다. 사용자가 아직 고르지 않았다.
> - 사용자가 확정하기 전까지 이 문서의 어떤 내용도 확정 규칙으로 인용하지 않는다.
> - 결정이 필요한 질문은 아래 "사용자가 답할 질문" 절에 번호를 붙여 모았다.
> - 추적 Issue: #4

## 맥락

### 사용자 의도

- [user] 제품은 사람과 AI 에이전트가 같은 대상을 동시에 편집하는 ADE(Agentic Dev Environment) 표면이다(인터뷰 §1).
- [user] 에이전트의 신원은 사용자의 대리인(delegated)일 수도, 독립 참여자(member)일 수도 있다(인터뷰 §4).
- [user] 에이전트는 로컬과 서버 어디서든 실행될 수 있다. **중요한 것은 프로토콜이다**(인터뷰 §4).
- [open] 에이전트가 사용자 문서를 고칠 때의 기본 동작. 인터뷰 기록에 "질문의 대상이 모호했다"고 남아 있다.
  그래서 이 ADR 은 "제안이냐 직접이냐"를 하나의 질문으로 묻지 않는다. **누가, 어떤 상황에서** 편집하는지로 나눠서 묻는다.

### 이미 확정된 제약

- **principal 모델** — ADR-0012 §3, [user]
  - `Principal = User | LocalUser | Agent`. 에이전트는 delegated 와 member 두 유형이다.
  - delegated agent 의 실효 권한은 (위임한 사용자의 권한) ∩ (사용자가 준 scope) 다.
  - 모든 쓰기에는 actor `{ principal, onBehalfOf? }` 가 남는다. presence, history, audit 에서 사람과 에이전트를 구분한다.
  - 에이전트의 쓰기와 권한 변경은 append-only audit log 에 남긴다(§5).
  - 에이전트의 편집 기본 동작은 이 ADR 에 맡겼다.
- **단일 policy** — ADR-0012 §1, **G1 (추인 대기, `ratify_by: 2026-10-03`)**
  - 권한 판정은 `authorize(actor, action, resource)` 하나로 한다.
  - HTTP, collab WebSocket, internal API, 앞으로의 에이전트 프로토콜이 모두 이 policy 를 부른다.
- **member agent 의 역할 저장** — decision log, **G1 (추인 대기)**
  - member agent 의 역할은 `WorkspaceMembership` 에 저장한다. 다시 볼 조건이 "이 ADR 에서 다른 모델이 필요해지면"이다.
  - 이 ADR 의 추천안은 이 모델을 **그대로 유지**한다.
- **쓰기 경로** — ADR-0011 결정 2, [user]
  - 문서 편집 상태의 write 정본은 Yjs document 다.
  - direct REST write 로 projection 을 고치지 않는다. 서버 쪽 Yjs mutation 을 거친다.
- **local 범위의 서버 접근** — ADR-0011, [user]
  - local 범위의 opt-in sync 에서 서버는 내용을 읽을 수 있다. 그래서 서버 에이전트를 쓸 수 있다.
  - 계정 없이 local 범위를 쓸 수 있다.
- **본문 정본** — ADR-0013 §2, [user]
  - `markdown` 타입의 본문 정본은 `Y.Text`(Markdown 문자열)다.
  - 선택 이유 가운데 하나가 "에이전트의 텍스트 도구(grep, diff, 텍스트 편집)와 가장 자연스럽게 맞는다"였다.
  - core 는 문서 타입을 모른다. 본문 구조를 아는 일은 type module 이 맡는다.
- **기존 경계 규칙** (사용자 결정은 아니다)
  - `docs/domain/rules/collaboration-boundaries.md` 는 MCP server adapter 를 앞으로의 에이전트 통합 표면으로 두고,
    "MCP tools/resources 는 application use case 를 호출한다"고 적는다.

### 현재 구현

- 에이전트, API token, service account 같은 사람이 아닌 actor 가 없다.
- 새 앱(`apps/editor`)은 슬라이스 1 이다. 브라우저 저장만 있고 서버 sync 와 협업 인증은 슬라이스 2 에서 붙인다.
- 제안(suggestion), 댓글, 변경 검토 기능이 없다. 과거 backlog 에서도 보류되었다(아래 "참고 자료").
- Yjs update 에는 작성자 정보가 없다. 누가 보냈는지는 연결의 clientID 로만 알 수 있다.

### 이 ADR 이 정해야 하는 것

사용자가 에이전트와 함께 일할 때 겪는 흐름을 따라가면 다섯 가지를 정해야 한다.

1. **연결**: 에이전트가 문서를 읽고 쓰려면 어떤 계약으로 붙는가.
2. **인증과 권한**: 에이전트가 누구로서, 어떤 범위까지 할 수 있는가.
3. **편집 반영**: 에이전트의 편집이 문서에 곧바로 들어가는가, 사람이 먼저 보는가.
4. **표시와 되돌리기**: 함께 편집하는 사람이 에이전트의 참여와 변경을 어떻게 알아보고 되돌리는가.
5. **이력과 출처**: 나중에 "이 문장은 누가, 누구의 요청으로 썼나"를 어떻게 답하는가.

## 후보안 1: 연결 프로토콜

### P1. Yjs/Hocuspocus 에 직접 참여

에이전트가 사람의 에디터와 똑같이 협업 서버에 WebSocket 으로 붙는다. Yjs 문서를 받아 로컬에서 고치고 update 를 보낸다.

- **장점**
  - 사람과 같은 경로다. 커서와 presence 가 자연스럽게 생긴다.
  - 문자 단위로 실시간 반영된다. 에이전트가 타이핑하듯 보일 수 있다.
  - 에이전트가 오프라인으로 고친 뒤 나중에 병합할 수 있다.
- **단점**
  - Yjs 바이너리 프로토콜과 문서 레이아웃(`meta`, `content`)이 **외부 공개 계약**이 된다. 협업 엔진과 레이아웃을 바꾸기 어려워진다.
  - 에이전트가 Yjs 라이브러리와 CRDT 개념을 알아야 한다. 대부분의 에이전트는 텍스트 도구로 일한다.
  - update 는 "텍스트의 어느 부분을 바꿨다"는 의도가 아니라 CRDT 연산이다. 서버가 update 단위로 권한과 모드(제안인지 직접인지)를 판정하기 어렵다.
  - 제안 모드를 만들기 어렵다. 보내는 순간 문서에 들어간다.
- **리스크**: 권한 없는 쓰기나 문서 구조를 깨는 update 를 서버가 걸러내기 어렵다. 공개 계약이라 되돌리기도 어렵다.

### P2. 제품이 정의한 문서 API (서버가 Yjs 에 반영)

에이전트는 "문서 읽기", "텍스트 범위 바꾸기", "제안 만들기" 같은 문서 단위 연산을 부른다. 서버가 policy 를 판정한 뒤 Yjs 문서에 mutation 으로 반영한다.

- **장점**
  - 공개 계약이 제품 언어(문서, 텍스트 범위, 제안)다. 협업 엔진이 계약 밖에 있다.
  - 텍스트 연산이라 에이전트의 텍스트 도구와 맞는다(ADR-0013 §2 의 선택 이유와 같은 방향).
  - 모든 호출이 `authorize` 한 곳을 지난다. 편집 모드 판정, audit, 속도 제한도 한곳에서 한다.
  - ADR-0011 의 "서버 쪽 Yjs mutation 을 거친다"는 규칙과 그대로 맞는다.
- **단점**
  - 에이전트 편집이 사람 편집보다 거칠다. 연산 단위로 반영된다.
  - 에이전트의 presence 를 서버가 대신 만들어야 한다(아래 "표시" 참고).
  - 오래 걸리는 편집 중에 문서가 바뀌면 기준 버전을 맞춰야 한다. 텍스트 앵커나 기준 버전 검사가 필요하다.
  - 서버가 없는 local 범위 문서에는 이 API 가 없다.
- **리스크**: API 설계가 부실하면 에이전트가 문서 전체를 통째로 덮어쓰는 식으로 쓰게 된다. 범위 편집을 기본으로 설계해야 한다.

### P3. MCP (Model Context Protocol) 서버

에이전트 생태계에서 널리 쓰는 MCP 로 문서를 resource 와 tool 로 노출한다. 도구를 구현하는 곳은 P2 와 같은 application use case 다.

- **장점**
  - Claude Code 같은 기존 에이전트가 별도 SDK 없이 바로 붙는다. 로컬 에이전트와 서버 에이전트 모두 쓸 수 있다.
  - 기존 경계 규칙(MCP adapter 는 use case 를 호출한다)과 맞는다.
  - MCP 권한 부여 흐름이 OAuth 기반이라 delegated agent 의 "사용자가 scope 를 준다"는 모델과 잘 맞는다.
- **단점**
  - MCP 는 요청-응답 중심이다. 문서 변경을 실시간으로 따라가는 데는 약하다.
  - 명세가 아직 빠르게 바뀐다. MCP 만 공개 계약으로 두면 명세 변화에 제품이 끌려간다.
- **리스크**: MCP 만 있고 그 아래 계약이 없으면, 다른 연결 방식(웹훅, 서버 내부 에이전트)을 붙일 때 로직이 중복된다.

### 추천: P2 를 계약으로, P3 를 첫 번째 연결 방식으로 — [agent]

- **공개 계약은 P2 의 문서 연산(application use case)** 이다. 협업 엔진은 계약에 드러내지 않는다.
- **첫 번째 연결 방식은 MCP** 다. MCP tool 과 resource 는 P2 의 use case 를 부르는 얇은 adapter 다.
  나중에 HTTP API 나 다른 방식이 필요하면 같은 use case 위에 추가한다.
- **P1(Yjs 직접 참여)은 외부 공개 계약으로 두지 않는다.** 제품이 직접 운영하는 신뢰된 에이전트에 한해 나중에 다시 볼 수 있다([open] Q2).
- 근거
  - 사용자가 말한 "중요한 것은 프로토콜"을, 에이전트가 어디서 실행되든 같은 계약으로 붙는다는 뜻으로 읽었다.
    P2+P3 는 실행 위치와 무관하다. P1 은 협업 엔진을 공개 계약으로 굳힌다.
  - 편집 모드(제안이나 직접)를 서버가 판정하려면 연산의 의도가 보여야 한다. P2 만 그렇다.

## 후보안 2: 인증과 권한

ADR-0012 가 principal 과 역할을 정했다. 이 ADR 은 **에이전트가 연결할 때 어떤 자격증명을 들고 오고, 어떤 action 이 필요한지**만 정한다.

### delegated agent 의 자격증명

- **A1. 동의 흐름으로 받은 scope token (추천)**
  - 사용자가 에이전트를 연결할 때 동의 화면에서 범위(workspace, 문서)와 action(읽기, 제안, 편집)을 고른다.
  - 에이전트는 짧은 수명의 access token 과 회수할 수 있는 refresh token 을 받는다. MCP 의 OAuth 흐름과 같다.
  - 장점: 사용자가 준 scope 가 token 에 명시된다. 교집합 규칙(ADR-0012 §3)을 그대로 계산할 수 있다. 연결 단위로 회수할 수 있다.
  - 단점: 동의 화면과 연결 관리 화면이 필요하다.
- **A2. 사용자가 직접 만든 개인 access token**
  - 설정 화면에서 token 을 만들어 에이전트 설정에 붙여 넣는다.
  - 장점: 구현이 단순하다. CLI 에이전트에 붙이기 쉽다.
  - 단점: token 이 오래 살고 유출되기 쉽다. scope 를 잘 좁히지 않는다.

### member agent 의 자격증명

- owner 나 admin 이 workspace 에 에이전트를 등록하면(`agent.manage`) 그 에이전트의 서비스 자격증명을 발급한다.
- 역할은 `WorkspaceMembership` 에 둔다(decision log G1 을 유지).

### action

- 에이전트에게도 ADR-0012 의 action(`content.read`, `content.write` 등)을 그대로 쓴다.
- **제안을 별도 action 으로 둘지** 정해야 한다([open] Q5).
  - 추천: `content.suggest` 를 새로 둔다. 제안은 "문서를 바꾸지 않고 변경안을 붙이는 쓰기"다.
  - 그러면 "이 에이전트는 제안만 할 수 있다"를 권한으로 표현할 수 있다. 편집 모드와 권한이 한 모델로 합쳐진다.

### 공통

- 모든 에이전트 요청은 `authorize(actor, action, resource)` 를 지난다(ADR-0012 §1, G1 추인 대기).
- 권한이 회수되거나 사용자의 권한이 줄면 에이전트의 다음 요청부터 거부한다. 진행 중인 연결도 끊는다.
- local 범위 문서에서는 기기 소유자(`LocalUser`)가 위임자가 된다. 서버가 없으면 이 흐름을 어디서 처리하는지는 [open] Q3 이다.

## 후보안 3: 편집 반영 방식

에이전트의 편집이 문서에 어떻게 들어가는지는 세 가지로 나뉜다.

| 방식 | 흐름 | 함께 편집하는 사람에게 보이는 것 |
| --- | --- | --- |
| **E1. 먼저 제안** | 에이전트가 변경안을 만든다. 사람이 수락하면 문서에 들어간다. | 수락 전까지 본문은 그대로다. 변경안이 표시된다. |
| **E2. 직접 편집, 이력으로 추적** | 에이전트가 문서를 바로 고친다. 변경은 이력에 남고 되돌릴 수 있다. | 바뀐 본문이 바로 보인다. |
| **E3. 적용 후 검토** | 에이전트가 바로 고치되, 변경을 "검토 대기"로 표시한다. 사람이 거절하면 되돌린다. | 바뀐 본문과 검토 대기 표시가 함께 보인다. |

### E1. 먼저 제안

- **장점**
  - 사람이 쓴 글이 사람의 확인 없이 바뀌지 않는다. 공유 문서에서 가장 안전하다.
  - 되돌리기가 필요 없다. 수락하지 않으면 끝이다.
  - 권한(`content.suggest`)과 자연스럽게 맞는다.
- **단점**
  - 사람이 모든 변경을 검토해야 한다. 에이전트에게 긴 작업을 맡길 때 흐름이 끊긴다.
  - 제안의 위치를 본문 변경에 맞춰 따라가게 해야 한다. 수락할 때 그 사이의 사람 편집과 충돌할 수 있다.
  - 제안 표시, 수락, 거절 UI 가 필요하다. 구현 비용이 가장 크다.

### E2. 직접 편집, 이력으로 추적

- **장점**
  - 가장 빠르다. 사람과 똑같은 협업자처럼 동작한다.
  - 제안 모델 없이 시작할 수 있다. 구현 비용이 가장 작다.
- **단점**
  - 사람이 쓰는 중인 곳을 에이전트가 바꿀 수 있다. 사람은 나중에 이력에서야 알게 된다.
  - 되돌리기를 에이전트 변경 단위로 제공해야 한다. 그 뒤에 사람이 같은 곳을 고쳤으면 되돌리기가 복잡해진다.
- **리스크**: 에이전트가 잘못된 대량 편집을 하면 모든 협업자가 곧바로 그 결과를 본다.

### E3. 적용 후 검토 (코드 에디터 에이전트 방식)

- **장점**
  - 결과를 문맥 안에서 바로 보면서도 사람이 최종 판단을 한다.
  - 코드 에디터의 에이전트 기능과 비슷해서 개발자에게 익숙하다.
- **단점**
  - 같은 문서를 보는 **다른 협업자**도 검토 전 변경을 본다. 한 사람 에디터에서는 괜찮지만 동시편집에서는 문제가 된다.
  - 거절할 때 그 사이의 사람 편집과 얽힌 변경을 되돌려야 한다. E1 과 E2 의 어려움을 모두 가진다.

### 누가, 어떤 상황에서 편집하는가

인터뷰에서 질문의 대상이 모호했던 이유는 상황마다 알맞은 답이 달라서다. 상황을 나누면 다음과 같다.

| 상황 | 예 | 위험 |
| --- | --- | --- |
| **S1. 사람이 방금 시킨 delegated agent, 요청자가 문서를 보고 있다** | "이 절을 요약해 줘" | 낮다. 요청자가 결과를 바로 본다. |
| **S2. 사람이 시킨 delegated agent, 요청자가 자리에 없다** | 긴 작업을 맡기고 떠난다 | 중간. 다른 협업자가 먼저 본다. |
| **S3. 스스로 도는 member agent** | 링크 정리, 정기 갱신 | 높다. 누구의 요청도 아니다. |
| **S4. local 범위의 개인 문서** | 혼자 쓰는 메모에 에이전트를 붙인다 | 낮다. 다른 협업자가 없다. |

### 추천: 기본은 제안, 허용된 경우에만 직접 편집 — [agent]

- **기본값은 E1(먼저 제안)** 이다. 특히 S2, S3 에서는 기본으로 제안한다.
- **직접 편집(E2)은 허용했을 때만** 쓴다.
  - delegated agent: 위임한 사용자가 연결할 때 "직접 편집"을 scope 로 줄 수 있다. 줄 수 있는 사람은 그 문서에 `content.write` 가 있어야 한다.
  - member agent: owner 나 admin 이 등록할 때 역할로 정한다. `editor` 면 직접 편집, 제안만 허용하려면 제안 전용 권한을 준다.
  - 즉 **편집 모드는 별도 설정이 아니라 권한으로 결정된다.** `content.write` 가 있으면 직접 편집할 수 있고, `content.suggest` 만 있으면 제안만 한다.
- 에이전트는 호출마다 원하는 모드를 고를 수 있다. 권한보다 강한 모드는 쓸 수 없다. 직접 편집 권한이 있어도 제안을 고를 수 있다.
- **E3 은 도입하지 않는다.** 동시편집에서 다른 협업자에게 미검토 변경이 보이는 문제가 제품의 기본 경험과 맞지 않다.
- S4(local 개인 문서)는 기기 소유자가 곧 위임자이므로, 연결할 때 직접 편집을 주는 것이 자연스럽다. 기본값을 다르게 둘지는 [open] Q7 이다.
- 근거
  - 공유 문서에서 사람이 모르는 사이에 글이 바뀌는 일은 되돌리기로 완전히 복구되지 않는다. 신뢰가 먼저 깨진다.
  - 권한으로 모드를 정하면 "편집 모드 설정"이라는 새 개념을 만들지 않고 ADR-0012 의 모델 하나로 설명할 수 있다.
  - 단점은 구현 비용이다. 제안 모델이 E2 보다 먼저 필요하다. 아래 "도입 순서"에서 다룬다.

## 후보안 4: 표시와 되돌리기

### 참여 표시 (presence)

- 에이전트도 presence 에 참여자로 보인다. 사람과 같은 자리에 두되, **에이전트임을 표시**한다.
  - delegated agent 는 "누구의 에이전트인지"를 함께 보인다. 예: "리뷰 에이전트 (홍길동 대리)".
  - 신원은 서버가 인증된 principal 로 정한다. 에이전트가 주장한 이름을 쓰지 않는다(ADR-0012 §1, G1 추인 대기).
- P2/P3 로 붙은 에이전트는 WebSocket 연결이 없다. **서버가 에이전트 대신 presence 를 발행**한다.
  - 에이전트가 문서를 읽거나 편집 중일 때 참여자 목록에 나타나고, 편집하는 범위에 커서나 강조를 둔다.
  - 연산이 끝나고 일정 시간이 지나면 사라진다.
- 모양의 세부(배지, 색, 커서 모양)는 UI 원칙(ADR-0014)과 `DESIGN.md` 안에서 G1 으로 정한다.

### 변경 표시

- **제안**: 본문 안에 변경안을 표시하고 수락과 거절을 제공한다. 누가 만든 제안인지 보인다.
- **직접 편집**: 에이전트가 최근에 바꾼 범위를 잠깐 강조한다. 문서의 이력 목록에서 "에이전트 변경"을 따로 볼 수 있다.

### 되돌리기

- 사람의 실행 취소(Ctrl/⌘+Z)는 **자기 편집만** 되돌린다. 에이전트 편집을 되돌리지 않는다. 지금 Yjs 의 기본 동작과 같다.
- 에이전트 편집은 **변경 묶음(한 번의 요청으로 생긴 편집 전체) 단위로 되돌린다.**
  - 되돌리면 그 묶음이 넣은 텍스트를 지우고 지운 텍스트를 되살린다.
  - 그 뒤에 사람이 같은 범위를 고쳤으면 자동으로 되돌리지 않는다. 겹치는 곳을 보여주고 사람에게 확인한다.
- 되돌릴 수 있는 사람: 그 문서에 `content.write` 가 있는 사람. delegated agent 의 변경은 위임한 사용자도 되돌릴 수 있다.

## 후보안 5: 이력과 출처

Yjs update 에는 작성자가 없다. 그래서 "누가 썼는가"를 어디에 기록할지 정해야 한다.

### H1. 연결 principal 로 update 에 작성자를 붙인다

- 서버가 update 를 받을 때, 그 연결의 principal 을 audit log 에 함께 기록한다.
- 장점: 모든 쓰기 경로(사람, 에이전트)에 똑같이 적용된다. 따로 모델을 만들지 않는다.
- 단점: 기록 단위가 CRDT update 라서 사람이 읽을 수 있는 "변경"이 아니다. 되돌리기와 제안 단위와 맞지 않는다.

### H2. 에이전트 변경 묶음을 제품 개념으로 둔다 (추천)

- 에이전트 요청 한 번이 하나의 **변경 묶음**이 된다. 묶음에는 다음을 남긴다.
  - actor `{ principal, onBehalfOf? }`
  - 대상 문서, 시각
  - 반영 방식(제안인지 직접인지)과 상태(대기, 수락, 거절, 적용, 되돌림)
  - 사람이 읽을 수 있는 변경 내용(텍스트 diff)
  - 에이전트가 남긴 설명(무엇을 왜 바꿨는지)
- 장점: 제안, 직접 편집, 되돌리기, 이력 표시가 **같은 단위**를 쓴다. audit log(ADR-0012 §5)의 에이전트 쓰기 기록도 이것을 가리키면 된다.
- 단점: 새 개념과 저장소가 필요하다. domain 문서와 모델 변경이 따른다.

### checkpoint 와의 관계

- checkpoint 는 사람이 의도적으로 만드는 이력이다. 자동 저장을 checkpoint 로 올리지 않는다는 기존 제품 원칙이 있다.
- 추천: 변경 묶음은 checkpoint 와 **다른 이력 항목**이다. 문서 이력 화면에서 checkpoint 와 에이전트 변경을 함께 보여주되 섞지 않는다.
- 큰 직접 편집 전에 자동으로 checkpoint 를 만들지는 [open] Q9 이다.

### 사람 편집의 작성자

- 이 ADR 은 에이전트 편집만 변경 묶음으로 추적한다. 사람 편집의 문자 단위 작성자 기록(blame)은 범위 밖이다.

## 결과 (추천안이 채택되면)

### 이 결정에 의존하지 않아 계속 진행할 수 있는 작업

- 슬라이스 2(동시편집): Hocuspocus provider, 협업 연결 인증, awareness 로 원격 커서 표시.
- ADR-0012 §1 구현: 단일 `authorize`, 서명된 collab token, `onAuthenticate`, internal 서비스 인증.
- presence 에 principal 유형(사람, 에이전트)을 담을 자리를 두는 것. 표시 모양은 이 결정 뒤에 정한다.

### 이 결정에 의존하는 작업

- 에이전트 principal 과 자격증명 구현(ADR-0012 결과 4 번과 함께).
- 문서 연산 use case 와 MCP adapter.
- 제안 모델, 변경 묶음 모델, 되돌리기.
- `docs/domain/` 갱신: 변경 묶음과 제안 모델, `content.suggest` action, principal 문서의 편집 모드 규칙.
  domain model 변경이므로 plan 과 함께 진행한다.

### 트레이드오프와 설계 부담

- **제안의 위치는 문서 타입이 안다.** core 는 타입을 모른다(ADR-0013). 텍스트 범위에 붙는 제안과 diff 는 `markdown`/`code` type module 이 제공해야 한다. core 는 변경 묶음의 저장, 권한, 상태만 맡는다.
- 제안과 변경 묶음을 Yjs 문서 안에 둘지(예: 별도 루트) 서버 저장소에 둘지는 구현 설계에서 정한다. local 범위에서도 동작해야 한다는 점이 제약이다.
- 제안 모델이 먼저 필요해서 에이전트 참여의 첫 출시가 늦어진다(Q11).
- MCP 명세가 바뀌면 adapter 를 고쳐야 한다. 계약(use case)은 영향을 받지 않는다.

## 검증 방법 (구현 뒤)

- delegated agent 가 위임한 사용자의 권한을 넘는 문서를 읽거나 쓰려 하면 거부된다. 사용자 권한을 줄이면 에이전트의 다음 요청부터 거부된다.
- 제안만 허용된 에이전트가 직접 편집을 요청하면 거부되거나 제안으로 처리된다.
- 두 사람이 같은 문서를 보는 동안 에이전트가 제안을 만들면, 두 사람 모두 본문은 그대로이고 제안이 보인다. 수락하면 두 사람 모두에게 반영된다.
- 에이전트의 직접 편집 뒤 사람이 Ctrl/⌘+Z 를 누르면 자기 편집만 되돌아간다. 변경 묶음 되돌리기는 에이전트 편집만 되돌린다.
- 이력 화면에서 에이전트 변경마다 에이전트, 위임한 사용자, 시각, 변경 내용이 보인다.
